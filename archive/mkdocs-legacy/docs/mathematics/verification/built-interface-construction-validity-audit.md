# Built-interface construction validity audit

This audit evaluates the mathematical validity of CALM's built-interface construction path and the extent to which the implementation realizes the interface-construction specification.

The audited implementation owners are:

- `calm.interface.pipeline.build_interface`
- `calm.interface._build_kernel.build_interface_atoms`
- `calm.interface.config.InterfaceBuildConfig`
- `calm.interface.model.Interface`
- `calm.ase_adapter.make_supercell_col`

The corresponding specification is `docs/mathematics/algorithms/interface-construction.md`.

## Audit scope

The audit concerns the deterministic build morphism that maps an interface prototype, a strain state, and a build configuration to a built interface structure:

```text
InterfacePrototype + StrainState + InterfaceBuildConfig
    -> Built Interface Structure
```

This audit does not validate whether the chosen candidate is globally optimal, whether registry optimization found a global minimum, or whether the interfacial-energy model is physically appropriate. Those are separate `Match`, registry-search, and `Evaluate` questions. Here the question is narrower: once the prototype, strain state, registry translation, and z-padding choices are fixed, does the build path assemble a geometrically coherent interface representation?

## Mathematical construction being audited

Given lower and upper slab structures, CALM applies the following operations.

1. Convert the two-dimensional supercell and rotation data stored on the prototype into embedded three-dimensional matrices.
2. Build slab supercells using CALM's column-basis convention through the ASE adapter.
3. Apply deterministic Cartesian rotations to both supercells.
4. Apply the recorded Cartesian deformation gradients `F_A` and `F_B`.
5. Read the strained lower-slab in-plane cell vectors `c1` and `c2` as the common interface basis.
6. Convert the fractional registry translation `(t1, t2)` to Cartesian form as `t1*c1 + t2*c2` and apply it to the upper slab.
7. Translate the lower slab so its minimum z-coordinate is zero.
8. Translate the upper slab so its minimum z-coordinate is separated from the lower slab maximum by `z_padding`.
9. Set a composite cell with rows `[c1, c2, (0,0,Lz)]`, where `Lz = h_A + h_B + z_padding + vacuum_padding` and `vacuum_padding` defaults to `z_padding`.
10. Concatenate atoms, record lower/upper index partitions, set full periodicity, and wrap positions.

This is a deterministic representation construction. It creates a new built interface structure, but several operations inside the construction are representation adapters rather than independent scientific choices.

## Mathematical validity assessment

The implemented construction is mathematically valid under the following assumptions.

### Compatible in-plane strain state

The strain state supplied to `build_interface` must produce a common in-plane metric after the prototype supercells, rotations, and deformation gradients are applied. The build kernel does not re-solve matching or re-derive the strain partition. It assumes the upstream `Match` and strain-partition steps have already supplied compatible matrices.

This is appropriate for the ontology: build is a downstream morphism from a candidate and a strain state, not a second match search.

### Column-basis to ASE representation adapter

CALM stores supercell transforms in a column-vector convention, while ASE expects row-oriented transform conventions. The build kernel delegates this adaptation to `make_supercell_col`. The audited code therefore avoids an inline transpose convention and centralizes the representation morphism.

The mathematical contract is:

```text
CALM column-basis transform N -> ASE supercell construction preserving the intended lattice generated by A N.
```

This is a representation morphism. It should not change the scientific identity of the selected prototype.

### Cartesian deformation and rotation

The helper routines apply Cartesian transformations consistently to positions and cell rows by right-multiplying row coordinates with the transpose of the Cartesian matrix. For a Cartesian map `x -> F x` expressed on column vectors, row-coordinate storage updates as `x_row -> x_row F^T`, and the cell rows update identically.

This is mathematically coherent, provided `F_A`, `F_B`, `R_A3`, and `R_B3` are expressed in the same Cartesian frame expected by the strain and prototype construction pipeline.

### In-plane registry translation

The fractional translation is interpreted in the post-strain common interface basis:

```text
t_cart = t1 c1 + t2 c2.
```

This is valid as a torus coordinate on the interface cell. Translation choices differing by integer combinations of `c1` and `c2` are equivalent after periodic wrapping.

### z-placement and vacuum convention

The lower slab is shifted so that its minimum z-coordinate is zero, and the upper slab is shifted so that its minimum z-coordinate lies `z_padding` above the lower slab maximum. The out-of-plane cell length is then:

```text
Lz = h_A + h_B + z_padding + z_vacuum.
```

When `vacuum_padding is None`, the implementation uses `z_vacuum = z_padding`. This is a backward-compatible representation convention, not a new scientific interface gap.

### Layer-index partition

The returned lower and upper index arrays are mathematically valid because they are assigned immediately after copying the lower supercell and before/after concatenating the upper supercell. This preserves the partition of atoms by slab origin, independent of subsequent wrapping.

## Correctness properties

A valid built-interface structure should satisfy these properties.

| Property | Expected invariant | Implementation status |
| --- | --- | --- |
| Input immutability | Input slab atoms are copied before mutation. | Implemented in `build_interface_atoms`. |
| Matrix shape validation | Supercell, rotation, and deformation matrices must be 3x3. | Implemented with `ValueError` guards. |
| Translation dimensionality | Registry translation has exactly two fractional components. | Implemented with `ValueError` guard. |
| Nonnegative z parameters | `z_padding` and explicit `vacuum_padding` are nonnegative. | Implemented with `ValueError` guards. |
| Common in-plane cell | Composite cell rows 0 and 1 equal the post-strain lower supercell rows. | Implemented by using `c1`, `c2` from the lower strained supercell. |
| z-spacing | Upper slab minimum z lies `z_padding` above lower slab maximum before final wrapping. | Implemented before wrapping. |
| Cell height | `Lz = h_A + h_B + z_padding + z_vacuum`. | Implemented. |
| Index partition | Lower and upper index arrays partition the concatenated structure. | Implemented. |
| Periodicity | Built structure is periodic in all three directions. | Implemented by `atoms.pbc = (True, True, True)`. |

## Implementation validity audit

The implementation appears valid for deterministic interface assembly. The most important positive findings are:

1. The code copies both input slab structures before applying supercell construction, rotations, deformation gradients, translations, cell replacement, concatenation, and wrapping.
2. Shape and parameter guardrails are explicit for all transform matrices and z-spacing parameters.
3. The column-basis/ASE adapter is centralized rather than duplicated inside the build kernel.
4. The lower/upper atom partitions are recorded after concatenation in a way that is independent of chemical species or positions.
5. Provenance fields are stamped at the pipeline level after the build UID and quantized translation are computed.

The main limitations are:

1. The build kernel does not independently verify that the post-strain upper in-plane basis equals the lower in-plane basis. That check is expected upstream in the strain/matching workflow.
2. The final `atoms.wrap()` means z-spacing assertions should be made before wrapping or with unwrapped helper fixtures. Post-wrap z coordinates are representation-dependent.
3. The legacy `Interface.build_interface` static method is a simpler historical build path and should not be treated as the canonical build morphism for new verification.
4. Validity depends on the deformation gradients being expressed in the expected Cartesian frame; this is documented by the interface-construction and strain-partitioning specifications but is not fully enforced by the build kernel.

## Verification status

The repository contains distributed tests for build behavior, public candidate build paths, registry runners, and UID/provenance boundaries. The most valuable additional tests are dependency-light build-kernel invariants that do not require full ASE availability.

Recommended test targets:

- shape and nonnegative-parameter validation;
- input-copy immutability;
- lower/upper index partition continuity;
- default `vacuum_padding = z_padding` convention;
- explicit `vacuum_padding` override;
- registry translation as a fractional coordinate in the common in-plane basis;
- pre-wrap z-spacing when using a minimal atoms-like fixture.

## Audit conclusion

The built-interface construction path is mathematically coherent as a deterministic geometry-assembly morphism, provided upstream matching and strain-state compatibility assumptions hold. The implementation appears to realize the intended mathematics for the canonical `calm.interface.pipeline.build_interface` and `calm.interface._build_kernel.build_interface_atoms` path.

The near-term verification need is not an implementation correction. It is stronger invariant testing around the build kernel and provenance continuity across build, evaluation, persistence, and report projection.
