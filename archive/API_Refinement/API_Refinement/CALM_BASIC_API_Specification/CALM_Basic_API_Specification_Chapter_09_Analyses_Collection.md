# CALM Basic API Specification

# Chapter 09 — Analyses Collection

## Purpose

The Analyses Collection is the public interface for computing,
managing, retrieving, querying, and exporting derived scientific
analyses.

It is the canonical owner of every persisted `Analysis` object and
represents the transition from atomistic simulation results to
scientific interpretation.

The Analyses Collection is responsible for deriving scientific
quantities from previously completed workflow stages while preserving
complete computational provenance.

The Analyses Collection does **not** perform structural relaxation or
modify scientific objects generated by earlier workflow stages.

---

# 1. Scientific Object

The Analyses Collection owns the following public scientific object.

```text
Analysis
```

An `Analysis` represents one or more derived scientific quantities
computed from existing project objects.

Examples include:

- interface energies,
- adhesion energies,
- work of separation,
- strain analysis,
- bonding analysis,
- coordination analysis,
- charge redistribution,
- structural comparison,
- custom scientific metrics.

An Analysis records both:

- the scientific inputs,
- the computed outputs.

---

# 2. Collection Ownership

The Analyses Collection is accessed through the project.

```python
project.analyses
```

Every persisted `Analysis` belongs to exactly one project.

An Analysis may reference one or more parent scientific objects,
including:

- Relaxation,
- Interface,
- Material,
- Surface,
- Match.

The parent objects depend upon the type of analysis being performed.

---

# 3. Lifecycle Responsibilities

The Analyses Collection is responsible for:

- computing derived scientific quantities,
- comparing scientific objects,
- storing analysis results,
- retrieving persisted analyses,
- querying analyses,
- exporting analysis results,
- deleting analyses.

The Analyses Collection does **not**:

- modify parent scientific objects,
- execute atomistic simulations,
- construct interfaces.

Analyses are read-only transformations of existing project data.

---

# 4. Supported Operations

| Method | Supported | Purpose |
|---------|:---------:|---------|
| `import(...)` | ✗ | Analyses are derived objects. |
| `create(...)` | ✗ | Analyses are produced computationally. |
| `generate(...)` | ✗ | Analysis is expressed explicitly as computation. |
| `run(...)` | ✓ | Compute one or more scientific analyses. |
| `compare(...)` | ✓ | Compare scientific objects. |
| `list(...)` | ✓ | Enumerate persisted analyses. |
| `get(...)` | ✓ | Retrieve one persisted analysis. |
| `find(...)` | ✓ | Query analyses. |
| `export(...)` | ✓ | Export analysis results. |
| `delete(...)` | ✓ | Remove persisted analyses. |

---

# 5. Behavioral Contract

## `run(...)`

Computes one or more scientific analyses from existing project objects.

Inputs depend upon the analysis type.

Examples include:

```python
project.analyses.run(
    interface_energy,
    relaxation,
)

project.analyses.run(
    adhesion_energy,
    relaxation,
)

project.analyses.run(
    strain_analysis,
    interface,
)
```

Execution produces one or more persisted Analysis objects.

Parent scientific objects shall never be modified.

---

## `compare(...)`

Performs comparative scientific analysis between multiple objects.

Examples include:

- compare interfaces,
- compare relaxations,
- compare surface terminations,
- compare MLIP predictions.

Comparison produces persisted Analysis objects.

---

## `list(...)`

Returns all persisted Analysis objects.

---

## `get(...)`

Returns one persisted Analysis.

---

## `find(...)`

Returns Analysis objects satisfying scientific criteria.

Typical criteria include:

- analysis type,
- parent object,
- constituent materials,
- calculation method,
- completion status.

---

## `export(...)`

Exports persisted analysis results.

Supported outputs may include:

- CSV,
- JSON,
- tables,
- publication-quality figures,
- reports.

Export shall never modify persisted Analysis objects.

---

## `delete(...)`

Removes persisted Analysis objects while preserving project provenance.

---

# 6. Scientific Transformations

Analyses are purely interpretive.

Unlike previous workflow stages, analyses produce no new physical
structures.

Instead, they derive scientific understanding from existing project
objects.

Every Analysis preserves references to its parent objects.

---

# 7. Object Relationships

An Analysis may consume several different scientific object types.

```text
Material
Surface
Match
Interface
Relaxation
        ↓
     Analysis
```

An Analysis never becomes the parent of another scientific object.

Datasets consume Analysis objects.

```text
Analysis
      ↓
Dataset
```

---

# 8. Scientific Questions

The Analyses Collection enables users to answer questions such as:

- Which interface is most stable?
- Which orientation is preferred?
- What is the interface energy?
- What is the adhesion energy?
- Where is strain localized?
- Which atoms reconstructed?
- How do two interfaces compare?
- Which MLIP produced the best prediction?

# 9. Example Workflow

```python
project = Project.open("lif_li2o")

relaxation = project.relaxations.get(relaxation_id)

energy = project.analyses.run(
    interface_energy,
    relaxation,
)

strain = project.analyses.run(
    strain_analysis,
    relaxation,
)

comparison = project.analyses.compare(
    energy,
    previous_energy,
)

project.analyses.export(
    comparison,
    "comparison.csv",
)
```

---

# 10. Design Rationale

Scientific analysis is intentionally separated from atomistic
simulation.

This separation provides several advantages:

- analyses are reproducible,
- analyses can be repeated without rerunning simulations,
- multiple analyses may consume the same scientific object,
- provenance remains explicit.

Grouping all scientific interpretation into a dedicated collection
provides a consistent public interface while preserving the separation
between simulation and scientific interpretation.

# Summary

The Analyses Collection owns every persisted `Analysis` object and
provides the public interface for deriving scientific understanding
from previously generated project objects.

It is responsible for transforming simulation outputs into scientific
results while preserving complete provenance and reproducibility.
